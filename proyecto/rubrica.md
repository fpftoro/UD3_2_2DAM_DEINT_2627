## Resultado de aprendizaje evaluado

Módulo profesional 0488 *Desarrollo de interfaces*, según el Real Decreto 405/2023, de 29 de mayo, por el que se actualiza el título de Técnico Superior en Desarrollo de Aplicaciones Multiplataforma.

**RA1. Genera interfaces gráficos de usuario mediante editores visuales utilizando las funcionalidades del editor y adaptando el código generado.**

| CE | Criterio de evaluación |
| --- | --- |
| a | Se han analizado las herramientas y librerías disponibles para la generación de interfaces gráficos. |
| b | Se ha creado un interfaz gráfico utilizando las herramientas de un editor visual. |
| c | Se han utilizado las funciones del editor para ubicar los componentes del interfaz. |
| d | Se han modificado las propiedades de los componentes para adecuarlas a las necesidades de la aplicación. |
| e | Se ha analizado el código generado por el editor visual. |
| f | Se ha modificado el código generado por el editor visual. |
| g | Se han asociado a los eventos las acciones correspondientes. |
| h | Se ha desarrollado una aplicación que incluye el interfaz gráfico obtenido. |


## Puntuación

Hay **15 criterios con el mismo peso**: 14 cubren todos los CE del RA1 (de la *a* a la *h*) y uno, sin CE, el flujo de trabajo con Git (criterio 15), como el proceso de diseño y la presentación en la UD1. Los CE con más trabajo en el proyecto tienen más de un criterio: el *d* (controles y estilos, accesibilidad), el *g* (eventos, comandos) y el *h* (enlace a datos, SQLite, inicio de sesión, errores, documentación). Los CE *a* y *e* se evalúan sobre todo en la **exposición**. Cada criterio se puntúa con uno de estos niveles, y la puntuación aparece en cada celda de la rúbrica, tal y como la configura Moodle:

| Nivel | Puntos |
| --- | --- |
| Sobresaliente | 10 |
| Notable | 8 |
| Suficiente | 6 |
| Insuficiente | 0 |

Moodle suma los puntos de todos los criterios (150 como máximo) y los convierte en la calificación final de forma proporcional: un proyecto con todos los criterios en Suficiente obtiene un 6 y uno con todos en Sobresaliente, un 10.

**Regla de autoría.** Si en la exposición el alumno no sabe explicar una parte de su aplicación, los criterios de esa parte bajan **un nivel**. Moodle no lo aplica solo: el profesor elige directamente el nivel rebajado y lo anota en el comentario del criterio.

## Requisitos mínimos

Para que el proyecto pueda considerarse superado, debe incluir como mínimo:

- La solución compila y la aplicación arranca.
- La aplicación tiene sus dos partes: la entidad con eventos y la entidad con MVVM, elegidas por el alumno.
- Los datos se guardan en SQLite.
- La exposición del proyecto.

Sin estos elementos, el proyecto se califica como insuficiente, independientemente de la puntuación del resto de criterios.

## Notas para la revisión

- **Todos los CE del RA1:** el proyecto evalúa los ocho. Los CE *a* y *e*, que en los ejercicios se trabajan con el test y el cuestionario, aquí se evalúan en la exposición (criterios 1 y 6).
- **Cada alumno tiene su dominio.** Los descriptores hablan de «la entidad con eventos», «la entidad con MVVM» y «la operación que relaciona» las dos entidades. **El alumno elige** cuál de las dos va en cada parte: no se penaliza la elección, solo que no esté justificada o que no se cumpla el reparto. Antes de corregir, lee la sección «Dominio y cambios respecto al diseño» del README de la entrega.
- **El modelo es del alumno y es pequeño.** Lo programa en este proyecto a partir de su diseño de la UD1; el criterio 9 mira que esté separado y sin WPF, que tenga las dos entidades, el gestor y al menos tres reglas con excepciones propias, no su sofisticación.
- **Pruebas (criterio 14):** se piden pruebas **unitarias** de los *ViewModels* (con repositorio y diálogos falsos), sin ventana ni base de datos. No se piden de integración ni de extremo a extremo: si las hay, no suben nota. Una prueba que abre una ventana o la base de datos no cuenta como unitaria. Si alguna prueba falla, anótalo en el comentario.
- **Dos partes en una sola aplicación.** La entidad con eventos y la ventana principal se hacen con eventos (criterio 7); la entidad con MVVM, la operación que relaciona y el inicio de sesión, con MVVM (criterios 8 a 13). Cada pantalla se programa de una sola forma: no se pide hacerla dos veces. Si una parte con eventos usa SQL o reglas del modelo en el *code-behind*, anótalo en el criterio 7.
- **Flujo de trabajo con Git (criterio 15):** sigue el material de Git visto en clase (ramas por funcionalidad, *pull requests* y *Conventional Commits*). No tiene CE porque el control de versiones no pertenece a ningún RA del módulo: pesa lo mismo que cada criterio con CE. Los mensajes de *merge* que genera GitHub (`Merge pull request #3 from usuario/feat/…`) no cuentan como mensajes propios. Si una rama se borró después de fusionarla, su nombre se lee en el mensaje del *merge*. Lo que no esté fusionado en `main` en la fecha límite no se corrige.
- **Trello:** no puntúa. Si el README no tiene el enlace, falta una parte de la sección «Planificación» (criterio 14). La tabla de ramas de esa sección se valora en el criterio 15.
- **Lista de controles (criterio 4):** cuenta que el control esté en la aplicación y sirva para un dato que le corresponda; un `RadioButton` puesto solo para cumplir, sin función, no cuenta. `MessageBox` cuenta si se usa desde el servicio de diálogos.
- **Inicio de sesión (criterio 12):** no se piden registro de usuarios, roles ni recuperación de contraseña. Pasar el `PasswordBox` como `CommandParameter`, leerlo con un servicio de la vista o usar un comportamiento adjunto son soluciones válidas; enlazar `Password` con una propiedad adjunta que lo copia a una propiedad de texto del *ViewModel* también funciona, pero deja la contraseña en memoria como `string`: vale si se justifica.
- **Sin propiedad de dependencia propia:** no se pide crear controles de usuario con sus propiedades de dependencia. Si el alumno lo hace, no sube ni baja nota.
- **Nivel Insuficiente a 0 puntos:** Moodle resta siempre la puntuación mínima posible antes de calcular la nota, así que el nivel más bajo equivale en la práctica a 0 aunque se le asigne otro valor.
